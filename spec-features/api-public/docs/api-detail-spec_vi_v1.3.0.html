1. Tổng quan

LME Public API v1 cho phép hệ thống bên ngoài đọc dữ liệu friend / tag / scenario / template / conversation của một bot LINE trên LME, gửi message cho friend, và thao tác hàng loạt trên friend (gắn tag, cập nhật friend info, chạy/dừng scenario, đổi trạng thái chat).

API làm được gì

  • Đồng bộ danh sách friend và chi tiết friend (tag, friend info, scenario).
  • Gửi message text / image / video / audio hoặc gửi template có sẵn.
  • Đọc danh sách conversation (lọc chưa đọc, trạng thái xử lý, tag) và 100 message gần nhất.
  • Chạy tối đa 10 action trên tối đa 100 friend trong 1 request (/do_action).

Phạm vi một API key

  • Mỗi API key gắn với đúng 1 bot. Mọi request chỉ đọc/ghi dữ liệu của bot đó.
  • Key quyền read chỉ gọi được GET; key quyền full gọi được mọi endpoint.
  • ID thuộc bot khác, đã xoá hoặc không tồn tại đều trả 404 not_found (không phân biệt "không tồn tại" và "không có quyền"). Nên cache danh sách tag / field / scenario / template ở phía bạn và làm mới khi gặp 404.

2.2 Xác thực

Phát hành key: trên màn hình quản lý API key của bot trong LME, chọn quyền (full hoặc read) và hạn dùng (để trống = vĩnh viễn). Key có dạng lme_live_sk_ + 32 ký tự hex.

LƯU Ý

LME chỉ lưu giá trị băm của key, không lưu key gốc. Hãy lưu key vào kho bí mật (secret manager / biến môi trường) ngay khi phát hành. Mất key thì phát hành key mới rồi xoá key cũ.

Gửi API key trong header X-LME-API-KEY ở mọi request. Không hỗ trợ truyền key qua query string hay body.

GET /v1/tags HTTP/1.1
Host: api.lmes.jp
X-LME-API-KEY: lme_live_sk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Thứ tự kiểm tra

Server kiểm tra theo thứ tự dưới đây và dừng ở lỗi đầu tiên — giúp suy ra nguyên nhân khi gặp nhiều vấn đề cùng lúc (ví dụ key read gửi POST sai Content-Type sẽ nhận 403, không phải 400):

  1. Thiếu header X-LME-API-KEY → 401
  2. Key không tồn tại → 401 "Invalid API key"
  3. Key đã xoá → 401
  4. Key hết hạn → 401
  5. Key bị vô hiệu hoá → 403
  6. Key read gọi method ghi → 403
  7. Method ghi thiếu Content-Type: application/json → 400
  8. Bot đã xoá → 403
  9. Vượt rate limit → 429
  10. Kiểm tra Idempotency-Key (chỉ POST có header) → 400 / 409
  11. Validate parameter / body của endpoint → 400 / 404 / 422

2.7 Rate limit

NhómMethodHạn mức
ĐọcGET300 request / phút / bot
GhiPOST60 request / phút / bot
  • Tính theo bot: nhiều API key của cùng 1 bot dùng chung hạn mức. Hai nhóm đọc/ghi đếm độc lập.
  • Cửa sổ cố định theo phút đồng hồ (fixed window): bộ đếm reset ở giây 00 mỗi phút (thời điểm trong X-RateLimit-Reset).
  • Chỉ request đã xác thực thành công mới bị đếm. Request bị 401/403/400-Content-Type không trừ hạn mức.
  • Request bị 429 không được thực thi. Chờ đúng Retry-After giây rồi gọi lại; không retry dồn dập.
  • /do_action xử lý tới 100 friend × 10 action chỉ tính 1 request ghi — gom thao tác vào một request thay vì gọi lẻ từng friend.
KHUYẾN NGHỊ

Đọc X-RateLimit-Remaining sau mỗi response; khi về 0 thì tạm dừng tới X-RateLimit-Reset. Với đồng bộ lớn, dùng limit=500 để giảm số request.

2.9 Idempotency & retry

Khi request POST bị timeout hoặc lỗi mạng, bạn không biết server đã xử lý hay chưa. Gửi header Idempotency-Key để retry an toàn mà không gửi trùng message / chạy trùng action.

POST/v1/do_action

Thực hiện hàng loạt action trên friend

Scope: fullRate limit: GhiIdempotency: hỗ trợXử lý: đồng bộ

Áp 1–10 action lên 1–100 friend trong 1 request: gắn/gỡ tag, cập nhật friend info, start/stop/resume scenario, đổi trạng thái xử lý, chặn/ẩn, favorite, đã đọc/chưa đọc.

Cách hoạt động

  • Mỗi action áp cho tất cả friend trong lmessage_friend_ids; các action chạy tuần tự theo thứ tự khai báo.
  • Toàn bộ request được validate trước — có 1 action sai thì không action nào được chạy.
  • Xử lý đồng bộ: response 200 trả về sau khi đã áp xong. Đặt timeout phía client đủ dài (khuyến nghị ≥ 60 giây cho request lớn).
  • Friend trùng trong mảng chỉ được xử lý 1 lần.
  • Friend không thuộc bot bị bỏ qua (không báo lỗi), các friend hợp lệ vẫn được xử lý. Chỉ khi tất cả friend đều không hợp lệ mới trả 404. Response không liệt kê friend bị bỏ qua — nếu cần chắc chắn, kiểm tra ID trước bằng /friends/detail.
  • Lỗi phát sinh khi áp action cho một friend riêng lẻ (sau khi đã validate) không rollback các friend khác và không làm request thất bại.

Tác dụng phụ cần lưu ý

  • tag.add: nếu tag được cấu hình hành động khi gắn tag trên LME (タグ追加時のアクション — gửi template, đổi rich menu, chạy scenario…), hành động đó chạy như khi gắn tag trên LME, có thể gửi message tới friend và tính vào hạn mức gửi tin. Chỉ áp cho friend chưa có tag đó.
  • scenario.start / resume: step được đặt gửi ngay (ví dụ step ngày 0 không hẹn giờ) sẽ gửi message tới friend ngay khi action chạy, và tính vào hạn mức gửi tin như message thường.
  • point_plus / point_minus và scenario.start không idempotent theo nghiệp vụ: gửi lại cùng request (không có Idempotency-Key, hoặc sau lỗi 500) sẽ cộng/trừ điểm hoặc chạy scenario thêm lần nữa.
  • Thay đổi qua API được ghi nhận như thao tác của người sở hữu API key trên LME.

  • Xử lý lỗi: thêm nhánh cho quota_exceeded (403 — không retry), in_progress (409 — retry sau vài giây), server_error (500 — retry có backoff).
  • Danh sách: chấp nhận field data.warnings có thể xuất hiện; dùng limit ≤ 500.
  • Media: dùng HTTPS, preview_url không redirect và ≤ 1 MB, audio luôn kèm duration, video luôn kèm preview_url.
  • Text: nếu nội dung có chuỗi dạng {name}, [date], [FRIEND_INFO_…], chúng sẽ bị thay bằng giá trị thật.
  • scenario.stop: dừng tất cả scenario của friend, không chỉ scenario truyền trong scenario_id.
  • Hạn mức gửi tin: nếu bạn ước tính hạn mức gói free theo số message, hãy đổi sang theo số request (1 request = 1 tin) — xem Cách tính hạn mức gửi tin.

9. Hỗ trợ

  • Khi gặp lỗi, gửi cho đầu mối WSSJ phụ trách: request_id (hoặc header X-Request-Id), thời điểm gọi (JST), method + path, HTTP status và error.code. Không gửi API key.
  • Nghi key bị lộ: xoá key ngay trên LME và phát hành key mới.
  • Góp ý về tài liệu (thiếu case, ví dụ sai, mô tả khó hiểu): gửi kèm số bản (ví dụ "1.3.0, mục 6 friend_info") để được cập nhật ở bản sau.
